# Checking Wave 3's repairs

Wave 3 opens with two repairs to the digest: a subject whose code is only in the
path, and a study whose date has to be found somewhere other than `StudyDate`
(`docs/specs/wave3-anonymize-and-bids.md`, §3 and §4). Both are about data that
is wrong in specific ways, so they are checked against a corpus built to be
wrong in those ways.

    # write the corpus and its manifest
    cargo run --release -p nils-dicom --example awkward -- \
        --out /scratch/nils/awkward > /scratch/nils/awkward-manifest.json

    # digest it
    nils init --registry REG --backend sqlite --scheme blake2b-8 --key k
    nils digest /scratch/nils/awkward --registry REG --files dcm,no-ext,DCM,IMA

    # and see what a correct reader would have found
    python3 tools/repair-check/check.py REG/registry.db /scratch/nils/awkward-manifest.json

The corpus is synthetic and the generator is the artefact: nothing in it derives
from any registry, so it can be regenerated by anyone from a seed and never
needs to be committed (design record, C10).

**It is meant to fail before the slices land.** Every failing scenario is a gap
the repairs close, and the manifest's `needs` field says what closing it takes.
A scenario that passes for the wrong reason is worse than one that fails, so the
corpus gives each person more than one study wherever a fallback could otherwise
produce the right count by accident.

v0's side of the comparison is the same pattern as `tools/pack-check`: v0's
identity and date functions are close to pure and importable, so a referee runs
them over the same tree and writes the rows v1 writes. v0 is private and is
never copied here; the referee imports it from wherever it is on the host.

## The gate

    sh tools/repair-check/gate.sh WORKDIR

Writes the corpus, digests **each scenario on its own with the identity rule its
manifest declares**, and checks the lot. One rule cannot read every layout: an
archive whose subject folder sits under a site directory has to be told so, one
whose tag is good needs no path source, and one whose code hides in a name needs
a pattern rather than a path. Digesting them all under one rule lets a scenario
pass for the wrong reason, which is worse than failing.

A scenario is right when it finds the people the manifest describes, dates every
study the way the manifest says, and raises the diagnostic the manifest expects.
That last one matters for the scenarios whose point is that the reader must
*speak*: a tag that is one constant across an archive, or a study whose files
name two different people. Diagnostics come from two places, and the gate reads
both: what the writer recorded per batch is in the registry, and what the run
concluded once every file had been seen is in the report.
