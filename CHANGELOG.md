# Changelog

All notable changes to NILS v1 are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html). The first release will be 1.0.0; until then pre-releases are tagged `v1.0.0-alpha.N`. The history of v0, the 0.x line, is in [kineuro/nils-legacy](https://github.com/kineuro/nils-legacy).

## [1.0.0-alpha.2] - 2026-09-10

### Added

- `nils setup`: one wizard that installs every part, makes what they need and writes down what it did. It is the other end of the one line installer: the script fetches the binary and the binary does the rest. Eight steps, each answerable by a flag and each skippable: **what to install** (the engine alone, the engine and the desk, or everything, which adds the assistant and the model gateway); **where it runs** (on the machine as two binaries, or in podman or docker containers, detected in that order); **where it lives** (one directory holding `registry/`, `desk/`, `backups/`, `working/`, `export/`, and a directory of DICOM the engine may read, which becomes an ingest root and a `source` place); **the registry** (a key passphrase asked for twice and never echoed, through the terminal's own echo flag rather than a new dependency, and SQLite or Postgres, the connection tried before anything is written so that a wrong connection string costs a sentence rather than half a registry); **who may sign in** (nobody, the desk keeps the people, or an identity provider, one answer setting the engine's `--auth` and the desk's `mode` together, and then who may open the desk, where choosing the network while nobody signs in says plainly that anyone on that network who finds the port gets the whole registry and offers the login instead); **what this machine can do**; **keeping it running**; and **the plan**, which is a summary before a single file is written. Where a default port is taken the wizard says which and moves that part to the next free one; where the ports are free it asks nothing.
- What the graphics card can serve, said before the assistant is offered and in the product's own words. `nvidia-smi`, then `rocm-smi`, then an Apple machine's unified memory: 24 GB or more fits a 27B model at 4 bit with room for the context, which is what the stations were written against; 12 to 24 GB fits a 7B to 14B model and the stations still work with more retries on the harder questions; under 12 GB or no card at all there is no local model worth serving, and the options are a model on another machine you can reach, a commercial provider through the gateway (the prompt then leaves the machine, and the gateway marks that backend remote), or no assistant at all, which costs nothing else. The wizard never installs a model.
- Containers as a first-class choice, not a port of the machine path. A podman run is one pod named `nils` publishing only the desk's port, the engine and the desk inside it, and `:U` on every bind mount so that a rootless container owns what it reads; a docker run is a network named `nils`, the desk publishing the port, and no `:U`, because docker does not remap the user. The images are `ghcr.io/kineuro/nils` and `ghcr.io/kineuro/nils-desk`; where an image cannot be pulled a Containerfile is written beside the base directory and the image is built there from the release binary already downloaded, and the wizard says so. The registry is made by the engine either way, running the key and the init steps inside a container against the mounted volume. Podman is kept running by quadlets in `~/.config/containers/systemd/`, docker by a `compose.yaml` in the base directory, the machine by systemd user units on Linux and launchd agents on macOS; where there is no service manager the commands are printed instead. Windows is refused with a sentence and a link, not a stack trace.
- The places a fresh install declares, in the order the registry's own rule needs: the backup place before the registry that names it, then the source directory where one was given, the working directory and the export directory. An engine that serves no places door says nothing and installs the rest.
- `~/.config/nils/setup.toml` (or `$XDG_CONFIG_HOME`), which is the wizard's memory: the base directory, the parts with their versions and how each one runs, the mode, the runtime, the service manager, the ports, the reachability, the backend and the places declared. Run `nils setup` again and it opens with what is installed, where, in what mode and how it runs, then offers to update everything, change something, add a part, or **repair**, which writes the configuration and the units again from what the state records, asking nothing.
- `nils update --all`: every part the state names, each in the way that part runs. A binary is replaced from its release as before, a container is a pull of the new tag and a restart of its unit with the unit rewritten to name it, a Node part is a fetch and a rebuild. One line each, and the engine last, since it replaces the binary doing the replacing. The desk's releases are its own repository unless `--channel` or `NILS_DESK_RELEASES` says otherwise.
- Prompting that survives `curl ... | sh`. Where stdin is a pipe the wizard opens `/dev/tty`, and where there is no terminal at all it takes every default and says so rather than waiting for an answer that will never come. `--yes` is the same thing on purpose, `NILS_NO_TTY=1` says it to a script that does have a terminal, and `--print` says what would happen, with the exact commands and unit files for both container engines, and changes nothing. Where there is no terminal to ask a passphrase on and no `--key-file`, one is made from the machine's own randomness and written to `<dir>/key.passphrase` readable by nobody else, with a line saying to move it into a password manager, rather than leaving a registry nobody can open.
- The assistant's two Node parts, installed the only way they can be: Node 22 checked, the repositories cloned and built, the gateway's `kvasir.json` written from its own example with the port this setup chose, an admin token made here and the address given for the model (a backend that is not on this machine is marked remote, and the wizard says that the prompt then leaves the machine), `assistant.env` written with everything the assistant reads, and the assistant's key minted at the gateway once the gateway answers, the command printed where it is not up yet. Where node is missing the wizard says so and installs the rest. It never installs a model.
- [`docs/guides/setup.md`](docs/guides/setup.md), the guide, and an installing section in the README.

## [1.0.0-alpha.1] - 2026-09-10

### Added

- `nils update`: the newest release over this binary, checked against the release's `SHA256SUMS`, written beside the old one and renamed over it; `--check` says what it would do, `--version` takes one, `--to` installs elsewhere, and `--channel` (or `NILS_RELEASES`) points the whole thing at a deployment's own release directory instead of the project's. The packs in use are refreshed with it when they are the user's to replace, and a release now carries `packs.tar.gz` beside the six binaries and their checksums.
- A pack directory a fresh install can find. Without `--pack-dir` or `NILS_PACK_DIR` the engine looks in the registry's own `packs`, then `$XDG_DATA_HOME/nils/packs` (else `~/.local/share/nils/packs`), `/usr/local/share/nils/packs`, `/usr/share/nils/packs`, and `share/nils/packs` beside the binary's prefix, taking the first that holds a pack; `nils serve` names the directory it took and `nils pack list` says where it read from.
- The repository: licenses, contributor terms (CLA and DCO), security and trademark policies, templates and CI, as the design record decided (`docs/decisions/`, R1 to R8).
- The engine skeleton (Wave 1 spec, §14, slice 1): the `engine/` Cargo workspace with `nils-dicom`, `nils-registry`, `nils-digest` and the `nils` binary, on Rust 1.98.0 pinned; CI formats, lints and tests on SQLite and Postgres 16 and builds `nils` on the six release targets; a tag now attaches the six binaries and their checksums to the release. The synthetic corpus generator moved from the spike to `tools/synth/`.
- The reader and the walker (Wave 1 spec, §14, slice 2). `nils-dicom` reads Part 10 files with or without the preamble and bare implicit or explicit VR data sets, stops before Pixel Data, carries the field catalogue (v0's 171 columns with their sources, fallbacks, converters and sensitivity classes, rendered to `docs/reference/catalogue.md`), the Enhanced functional-group and private per-frame fallbacks, the six DWI private values by creator block, the character set handling, the seven quarantine classes and the diagnostics. `nils-digest` walks a root with a pool of listing threads (symbolic links skipped, an unlistable directory a `walk_error`, an unlistable root the job's failure), filters names with the `files` knob and feeds a pool of parsers. `nils digest <root> --dry-run` reads everything and prints the report (counts per quarantine class and diagnostic kind, studies, series, subjects, modalities, SOP classes, transfer syntaxes, character sets, rate, peak RSS); `--describe` prints the knobs; `--json` for both. Over the nmosd corpus (508,045 files) it refuses the 134 files the spike refused, at 62,300 files/s on eight workers.
- The schema and the writer (Wave 1 spec, §14, slice 3). `nils-registry` declares the registry and the linkage store once as data (fifteen and six tables, the catalogue's columns typed from the reader's declaration) and renders them for SQLite and Postgres through a small dialect layer with numbered migrations, a key store (`nils key`), and the bulk paths: multi-row inserts on SQLite, `COPY` into temporary tables merged with `INSERT ... SELECT ... ON CONFLICT` on Postgres (`NILS_PG_BULK=insert` selects multi-row inserts there too). A registry is a home directory with `nils.toml` (`--registry`, `NILS_REGISTRY`, `NILS_DSN`); `nils init` creates one on either backend. `nils digest` now writes: one transaction per batch, subjects under the pseudonym scheme (the identity rule is fixed until slice 4), studies, series and their modality tables, instances, every path with its status, the diagnostics and the epoch; a known row is never rewritten, a stored null is filled by the first file that has a value, and a file that disagrees raises `field_disagreement`. Resume by default: unchanged files are skipped by `(size, mtime_ns)`, quarantined ones kept unless `--retry-quarantine`, changed ones re-read and filed with a `file_changed` diagnostic, and a complete unfiltered walk marks the paths it did not see `gone`. Jobs: a job row with a heartbeat, refusal while another job is fresh (exit code 3), takeover of a stale one, and `nils status`. The synthetic generator became the `corpus` example of `nils-dicom`, writing the files with the crate's own Part 10 writer. The synthetic million (1,011,783 files, 2,000 of them refused by design) digests to identical counts on SQLite, Postgres `COPY` and Postgres `INSERT`: 32 s, 65 s and 70 s on 64 workers from cache, at 2 GB peak RSS with the batch queue capped at sixteen (it was 4 GB uncapped); the numbers are in the spec, §9.2.
- Identity (Wave 1 spec, §14, slice 4). The two pseudonym schemes (`blake2b-8`, v0's function byte for byte, and `blake2b-32` with its display code), the subkeys of the linkage store derived from the registry's one key, the identity rule as a YAML file (`nils digest --identity-rule`: fields in order, a pattern with an `id` group, the study UID as the fallback), and the writer's resolution through the linkage store: a returning identifier is one subject across studies and runs, an imported code is kept, a subject holds one identifier per type, and two identifiers on one code roll the batch back, open an `identity.collision` review item and fail the job without naming an identifier. `nils linkage import` files a CSV of legacy codes validate-then-apply; `linkage id-type add | list`, `linkage show --why` (decrypts, writes `read_audit`), `linkage link` and `linkage unlink` exist as the spec lists them. A linkage store carries its registry's id and is refused next to another registry. The report gained `subjects_matched` and `identities_attached`. `serde_yaml` gave way to `serde-saphyr`.
- Stacks (Wave 1 spec, §14, slice 5). Every instance is filed under a stack of its series, decided from the file alone by v0's signature: fourteen values in v0's order and rounding (the MR timing, echo and coil fields, the CT exposure fields, the PET bed and frame type, the orientation class from ImageOrientationPatient by v0's cross product, and ImageType), keyed by BLAKE2b-8 of a canonical string. The `stack` row carries the key, the index in order of first appearance across batches and runs, the class, the confidence and the fourteen values as read; the instance points at it from the transaction that files it. A known orientation under 0.9 counts `orientation_oblique` once per stack created; the thirteen series-level columns a signature is also made of are left out of `field_disagreement`, because instances that differ on them are the series' stacks. The report and the dry run count `stacks`, and `written` counts `stacks_created`. On the nmosd corpus v1's partition equals v0's, recomputed with v0's own code (`spikes/stacks/`), on every one of the 2,165 series both hold: 2,534 stacks, 2,534 v0 groups, over 493,708 instances.
- Jobs, resume and custody (Wave 1 spec, §14, slice 6). One signal stops a digest (what is parsed is written and committed, the batch is `cancelled`, exit code 130) and a second abandons the batch in flight; a job whose process is gone is taken over at once; a failed batch records `reparse_from` so that the run that resumes it reads its last second again and repairs a registry commit that lost its linkage commit. The kill-and-resume tests (`NILS_DEBUG_STOP`, a test hook) show a run killed after a commit, killed inside a transaction, stopped, aborted or interrupted resuming to the same rows as an uninterrupted one, on both backends. `nils custody [--json | --markdown]` lists every store a registry keeps (the configuration, the registry, the linkage store, the key store, the quarantine list, the job records, the logs) with where it lives, what it holds, how long, and the commands that read, change, export and delete it; the test checks that every file under the home is listed and every command named exists, and `docs/reference/custody.md` is the page for a SQLite home. `nils quarantine list` prints the refused files with class and detail, one `ingest.quarantine` review item per batch and class is filed with the count as evidence, `nils review list | show` read the items, and `nils linkage purge --subject <code> | --all` deletes a subject's identifiers and linkages after saying what it would delete, keeping the read audit and recording itself as a job. Unchanged files no longer pass through the parsers' queue (the resume stage batches them for the writer itself): a second pass over an unchanged half-million-file tree takes 4.7 s where it took 25.8 s, on any number of workers.
- The compare tool (Wave 1 spec, §14, slice 7). `tools/v0-compare/` (Python over DuckDB) reads a v0 registry through `export.sh`'s read-only CSV export or a DSN and a v1 registry on SQLite or Postgres, and measures the gate of §12: every v0 instance in v1 or explained by name, every v1 instance in v0 or explained (v0's file mode, its nine SOP classes, its modalities, its resume rule, a series v0 never wrote), every field agreeing after both sides are brought to one normal form (v0's list literals to the backslash form, canonical numbers, ISO dates and times, JSON as presence, v0's rounding on the six rounded stack columns), the stack partitions matched by membership, every v0 subject code a v1 code with every study on the same code, and v1's sessions against v0's events. Divergences are grouped by field and pattern as shapes, never values, and an adjudication file classes each group `v0-bug`, `v1-bug` or `accepted`; a group in the first or the last class is excused from the bar it would fail, the others count in full, and the report (`report.md`, `report.json`, counts and shapes only) ends with the bars and an exit code. `linkage-csv` writes the CSV `nils linkage import` takes, counting collisions; `--key-file` classes how v0 derived each code. The walker's `files` knob takes a comma-separated union (`--files dcm,no-ext` is v0's "all"), the corpus generator gained `--same-day-percent`, and a `v0-compare` CI job projects a v0-shaped export out of a synthetic registry with injected divergences and checks that each lands in its class and a clean one passes, on both backends.
- What the first gate run taught the compare tool (Wave 1 spec, §12.1 to §12.3, slice 7). A SQLite registry is read by its declared types rather than as text, since SQLite spells a REAL with 15 significant digits and a float32 widened to a double needs 17, which made hundreds of series differ on the spelling alone. The thirteen stack-signature columns of the series tables are derived from the catalogue as the engine derives them, and a divergence of one of them in a series with several stacks on either side is grouped apart (` (multi-stack)`) and classed `accepted` by the tool itself: the series row carries the first instance's value on both sides and which instance is first follows the walk order; the same field in a single-stack series still needs a rule. A v0 path absent from the compared root is reported apart when its subject is listed under several cohorts, since a v0 path is relative to its own cohort's root; `--fs-cap` bounds the on-disk check (a million paths by default, `0` for all of them) where it used to stop silently at a hundred thousand. `export.sh` counts lines, not rows.
- A row's fields are decided, not raced (Wave 1 spec, §8 and §9.1, slice 3 amended in slice 7). Where two files of one subject, study or series disagree on a column, the row keeps the smaller value in the catalogue's canonical text order instead of the first one written, on every column of those rows; the fill rule covers every column too. The registry no longer depends on the order the walk and the workers gave the files, which the first gate run showed to be real: single series carry up to twenty-six spellings of `sequence_name`, two acquisition matrices, two slice spacings and two orientations. `min` needs no bookkeeping, so a resumed run, a late batch and a second digest of one tree reach the same row; the writer reads a field's stored value once, the first time that field of that row is disagreed about, and keeps it with the cached row.
- A person may hold several identifiers of one type (Wave 1 spec, §7.3 and §7.4, slice 4 amended in slice 7). `nils linkage import` files any number of identifiers of one type on one subject instead of refusing the second, and counts the ones that joined a code another identifier already named: a personnummer is not for life, since a temporary number becomes a permanent one when residency is granted, several temporary ones may come before that, and the permanent one changes when a legal sex change does. Only an identifier that maps to two codes is still refused, and two identifiers that derive one code by the scheme's function are still a collision. The identity rule gained `code: verbatim`, which files the value it reads as the subject code instead of deriving one, for data pseudonymized before it reaches us; it requires a pattern on every field, so a value that is not shaped like a code is never filed as one, and a file that does not match takes the fallback as always.
- Files whose elements declare a length their VR cannot hold are read, not quarantined (Wave 1 spec, §6.1, slice 2 amended in slice 7). One vendor's private block writes a `UL` of six bytes, where a `UL` takes four; `dicom-rs` reads the values that fit but counts the whole length as consumed, so the stream runs two bytes behind and the file looks truncated. The reader now repairs such a file in memory when the first read failed as truncated: it walks the header, rounds each impossible length down to the values that fit, drops the surplus bytes and reads the repaired copy, counting a `ragged_length` diagnostic. The file on disk is never touched. On the mix corpus this recovered 1,996 files of 196,086, and with them 69 series, 47 studies and 32 subjects.
- The budget, measured (Wave 1 spec, §14, slice 8; §12.5 and §12.6). On an 8 vCPU / 64 GB virtual machine reading the corpus from the storage server over NFS, from a cold cache, v0 digests one study's raw tree of 497,150 files in 981 s at 507 files/s and 5.78 GiB, and v1 in 87 s at 5,713 files/s and 0.83 GiB, with the same counts on both sides: eleven times the rate at a seventh of the memory. On Postgres 16 v1 takes 93 s; a second pass over the unchanged tree takes 4.2 s. The gate of §12 passes on that host too, every bar. A `bench` job in CI writes 200,000 instances from a seed, digests them and fails the build when the rate falls below 80 percent of the recorded baseline or the memory rises above its cap (`engine/benches/`).
- The fingerprint (Wave 2 spec, §4 and §13, slice 1). A new crate, `nils-classify`, and a new table, `stack_fingerprint`, added by migration 2 so that a registry written before it opens under this binary without being rebuilt. `nils fingerprint` derives one row per stack: the six text fields v0 joins, each folded and once more as the join (Unicode NFKC, whitespace collapsed, **case kept**, because a pack's first normalizer step is a case-sensitive removal); the multi-valued fields as read, since a parser declares its own tokenizer; the physics, the stack's own value where it has one and the series' otherwise; the shape, the provenance and the contrast administration; and v0's field of view, from the stack's first instance **by SOP Instance UID** rather than by row id, which is Wave 1 §15's open item closed on the deterministic side. It is a job like the digest, with the same takeover of a dead one, a heartbeat, a stop between windows and a resume that is a predicate over columns: a stack already derived whose instance count still agrees is skipped, one that gained an instance is derived again, and `--force` overwrites. What the fingerprint does **not** hold is the decision the slice turned on: no flags and no semantic normalization, because both are derived by a pack's grammar. The fingerprint holds what is true of the file; a pack holds what is true of the knowledge, and correcting the token map is then a pack version rather than a re-extraction of the archive. It does carry one thing v0 computes and never reads: **why a series split**, the first signature column its stacks disagree on in v0's order, which three of v0's flags test for and none of them ever receives. v1's derivation agrees with v0 on all 2,165 series of the nmosd corpus and on 2,559 of the mix corpus's 2,567; the eight are v0's own, and their cause is named: v0 writes the key in its sort step and not in extraction, so all 19 multi-stack series in the archive without one are exactly the 19 that were never classified. On CT 110 the pass costs 0.8 s for nmosd's 2,534 stacks and 0.4 s for the mix corpus's 4,120, at 0.08 GiB, against the 30 s and 87 s their digests took.
- The pack loader (Wave 2 spec, §5 and §13, slice 2). A new crate, `nils-pack`, which knows nothing about a registry: a pack plus a stack yields facts, which is what makes a pack testable from a fixture and shippable by someone who has never seen our schema. It loads a manifest (name, semantic version, contract, modality), the parser and flag layers, and the pack's editable **buckets**; it refuses a contract it does not implement, a version that is not semantic, a name that resolves to nothing, a pattern that will not compile, a flag that depends on itself, and a parser declared twice, each **by file, line and path**, because a pack is written by someone who writes vocabulary rather than Rust. **Overlays** (C2) are provenance-scoped and refused when scoped by a selection; the merge is v0's rule exactly, duplicates dropped case-insensitively with the first spelling kept and the order of writing preserved, since v0's contrast vocabulary contains terms whose leading space is load-bearing. The pack's own **corpus runs at load** and its failure is the load's failure, which is what makes a pack from elsewhere safe to install. Whose cases judge what was settled while building: the pack's corpus judges the pack, un-overlaid, and an overlay carries its own cases and is judged by those, because running the author's claims against a site's amendment makes the claims a constraint on the site. `packs/mri/` holds the parser and flag layers the C11 prototype verified against v0 over 518,365 stacks, now with 18 cases of its own; `nils pack list | show | validate` read them.
