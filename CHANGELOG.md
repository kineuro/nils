# Changelog

All notable changes to NILS v1 are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html). The first release will be 1.0.0; until then pre-releases are tagged `v1.0.0-alpha.N`. The history of v0, the 0.x line, is in [kineuro/nils-legacy](https://github.com/kineuro/nils-legacy).

## [Unreleased]

### Fixed

- An install survives a reboot. `nils setup` wrote the units of Kvasir and the assistant as `ExecStart=/usr/bin/env node ...`, which looks Node up on the service manager's PATH, and at boot the user manager's PATH does not yet hold `~/.local/bin`, where a Node of an account's own is linked. Both services exited 127 five times and stayed down until somebody started them by hand, while after a login the same units ran, which is why no test ever saw it. Setup now finds the Node it builds them with, the first Node 22 or newer on its PATH, and every unit names it by that absolute path, as the engine, the desk, llama.cpp and the supervisor were already named; the path is kept as it was found, so a Node replaced behind its link is the one that runs. The install records it as `node`, so that an update run from a PATH with no Node on it, as a service's can be, writes the same one again, and `nils update --all` writes every unit again as it always has, so an install made before this is mended by its next update. Where no Node is left, neither on the PATH nor at the recorded path, the update says so and the unit falls back to the manager's PATH, and the supervisor's install report carries `node` with its path, whether it is still there and what to do if it is not. Units in containers are unchanged, since the image has its own Node.

- A `run-` index means a repeat, and two different acquisitions never share one name in silence. BIDS gives `run-` to one acquisition measured again, and the release wrote it wherever two stacks of one subject, session and datatype came out with the same filename. Measured over a corpus of 702 named stacks, 403 of them took a `run-` index and 270, 67 per cent, sat under a name that covered more than one acquisition; over a legacy archive of 437,069 classified stacks, only 18 per cent of colliding names are repeats at all. A `run-2` that is really a different echo time is a claim nothing downstream can audit, because a validator passes it and a reader believes it, and the groups are small, so it has always looked exactly like an ordinary rescan. The index is now issued only where the two stacks are measurably the same acquisition, and the test is declared rather than hidden, so a person can argue with it and two releases agree: two different series, every axis the pack decided equal, the coverage not differing, the receive coil equal, the protocol name equal once the counter a scanner appends to a re-run step is taken off it, the echo time, repetition time, inversion time, flip angle and b value within two per cent, the slice thickness and spacing within five, and the averages, echo train length, acquisition matrix, image size, scan options, scanning sequence and sequence variant equal exactly. A value only one side recorded is not a difference, because an absence is not a measurement; a whole group is one acquisition only when every pair in it is. Where a name covers more than one acquisition, no name is written at all: the stacks go to `sourcedata/` under the informative names of the descriptive layout, which are unique, and one review item per name says which stacks they are and what differs between them, in the pack's own words, which is also the evidence a new axis would need. A group whose suffix admits no `run-` at all is handled the same way, where before the second stack silently rewrote the first. The report says the three numbers behind every index the tree carries, `shared_names`, `repeats` and `not_repeats`, `nils release` prints them, and the tree's README says what its own `run-` indices are worth, because a silent change here is what caused the problem.

- A release report names the categories it applied. A release has recorded which categories of element it removed since there were categories to record, because "de-identified" is not a property a file can carry without saying under what rule, and it recorded them on its row alone: not in the report it prints, not in the JSON one, not in `/api/releases`. So the sixth category landed, the accession number and the device serial number started leaving the archive, and the only thing a person reading a release could see was that two more tags had moved. The report now names them, in the order they were given, and where fewer than all six were applied it names the rest too, because what a release left in is the half of that sentence an operator has to see: `categories patient, ids` and `not removed trial, provider, institution, times; those elements leave the file unchanged`. `nils release --history --json` and `/api/releases` answer with the same names, read off the release row, so the report and the door cannot say different things about one release.

- `nils classify` counts stacks as stacks and items as items. The line a person reads first said `review items 830, 99.3% of the stacks, as 58 question(s)`: 830 is a count of items, 836 is a count of stacks, and the share was one divided by the other. Only 546 of those 836 stacks, 65.3 per cent, carried anything for a person at all, because one stack can raise a conflict and a weak answer and a split all at once and be three items in that total. The run now counts the distinct stacks its questions stand on, from the members it wrote, and says three numbers against the three things they count: `stacks to review 546, 65.3% of the 836 classified` and `review items 830, on those stacks, as 58 question(s)`. The share is stacks over stacks, the denominator is printed beside it, and every one of the three can be read back out of the registry. The JSON report carries the new count as `review_stacks`.

- A release removes the accession number, and the other direct identifiers its categories had never named. The five categories were carried from v0 tag for tag, and `(0008,0050)` was in none of them, nor `(0018,1000)`: a release wrote the hospital's own identifier for the examination, and the serial number of the machine that made the images, through to the released file verbatim, on every file it has ever written, while the change list it records said nothing about either, so nothing a reader could open said the elements had even been there. An accession number in the hands of somebody who can reach the hospital's systems undoes everything else a release did. A sixth category, `ids`, is the home those elements never had: 47 elements measured against DICOM PS3.15 Annex E's basic profile, holding the accession number and the issuer that says whose numbering it is, the study, admission and service episode ids with their issuers, the placer and filler order numbers, the machine's serial number, its own UID, the gantry, the unique device identifier and the stations, AE titles and locations the step was scheduled and performed at, the identifying, study, acquisition, image and visit comments and the description of the constraint on the patient's data, which are where a name, an accession number or a telephone number gets typed, the patient's birth name, alias, photograph, responsible organisation, issuer qualifiers, ward and institution of residence, the intended recipients of the results, who entered the order, from where and on which telephone, the bare person name of the content items, and the retired results and interpretation elements an old archive still carries. It goes with the other five by default, because the safe set is the one nobody had to think about, it is named `ids` where a run picks its categories, and the categories a run applied are recorded on the release as they always were. The change list names each element it removed and how many files it came out of, so a reader sees that an element was handled rather than absent by luck.

- The set is considered rather than complete, and what is left in is left in on purpose. The study and series descriptions, the protocol name and the sequence name stay: they are the evidence a pack classifies on and the only thing that lets a released tree be read or judged again, and they were read at digest long before a release writes. Dates stay under the date policy and UIDs under the UID remapping rather than joining a category, because two policies on one element is how one of them comes to be forgotten. Beside the categories the engine now holds one list of its own, what may never survive a release: the direct identifiers across every category that holds one, written out rather than derived from the categories, since a list built from what the code removes can only ever agree with the code, which is how an accession number was written through for as long as it was. A test writes files carrying every element on that list, releases them, and fails with the element's number if one comes out the other side or its value is still in the bytes. What the pseudonymiser removes is unchanged, so the tag policy it serves is the one a client already read.

- A release counts the stacks whose file will not say whether their pixels carry text, and no longer keeps them. Wave 3 section 8.4 says a stack whose `BurnedInAnnotation` says yes, or whose image type carries a token that means a picture of a screen, raises a review item and is not written, and that where the tag is absent the release says how many stacks it could not judge. The code held that third answer as well, and `BurnedInAnnotation` is absent on most of the series of a real archive: a default release of a selection reaching 772 stacks wrote 174 of them, most of its subjects released nothing at all, and the number a release was supposed to print was the number of stacks it was keeping. The tag saying yes and the screenshot token hold a stack exactly as they did; an absent tag does not. Such a stack is written and counted, and the count is in the report, under `could not judge` beside the stacks held back, and in the release's own row, as `unjudged` beside `burned_in`, with `policy.on_unknown` beside them saying what was done with them, since the same number reads one way under each setting. `--on-unknown` is unchanged in spelling and gains a default: `write`, which writes and counts, and `hold`, which holds every unjudged stack and files a question about each, as the default did. A site that wants what it had asks for `hold` on the command line or at the release door; a site that does not now releases what it selected and reads one number about what nobody can judge. A dataset released before this and released again under the new default gets its unjudged stacks as stacks added to the next version, and the stacks it already wrote are rewritten once, because the run's own policy is part of what decides a file's bytes.

- A stack held back by a release is asked about once, and not again by every later release. A release is re-run whenever anything upstream of it changes, and the file says the same thing about its pixels every time, so a question per held stack per release is the same question filed again: two releases of one selection filed two queues of identical rows, hundreds each, and a queue nobody can read is a review spine that has stopped working. A stack that already carries a `release.burned_in` or a `release.unjudged` item, answered or not, raises no second one, whatever the release. What recurs is the count in the report and in the release row, which is where a fact about a whole run belongs. Nothing closes or rewrites the items already filed.

- The body-part rules read the value before anything removes its words. The MRI pack's normalizer drops `brain` and `head` as boilerplate, which is right for the axes that tell techniques and constructs apart and wrong for the one axis those two words are the answer to: on a run over an archive of 836 stacks, 607 of the 636 whose `BodyPartExamined` says `BRAIN,HEAD` came out with no body part at all, while `SPINE` and `NECK`, which are not on the removal list, decided 71 of 71. Nothing was flagged, because an axis with no value is a question only where the pack says a value is always expected, so it read as success. The pack now derives a second text, `anatomy_text`, from the same six fields with the same folding and none of the removals, and every clause of the body-part rule set reads it: the stated body part decides, whatever the description says, and a description that mentions anatomy is no longer blinded by a word dropped for somebody else's benefit. The removals stay exactly as they are for `search_text`, so no other axis moves, and the damaged and accented spellings still fold to the gap the keyword lists are written with. The pack's own corpus carries the six cases that say so, including the one that shows the boilerplate is still boilerplate where it was meant to be.

- A neck a rule can name is a neck the axis can produce. The body-part rules are ordered and the first to fire decides, so a rule ahead of another has to be the narrower of the two: `brain_neck` asks for a neck word and a brain word where `neck` asks for the neck word alone, and that holds only while the two read the same neck words. `cou`, the French for it, is three letters, and a keyword is matched as a plain substring anywhere in the text, so it fired inside ordinary words. On an archive it was never once the word a verdict cited: it was found behind the spine rule on 6 stacks and, after the wave gave the body-part rules a text with nothing dropped from it, behind the brain-and-neck rule on 35 more. Those 35 are series whose file states their body part as a brain, and a fragment of a longer word made each of them a neck beside a brain, while the rule that can name a neck sits behind that one and was reached by nothing: the axis had four values and could produce three. The word is spelled as a word now. The anatomy normalizer expands the token `cou` to `neck`, which is what the other normalizer's expansions are for, and `cou` is a keyword in no rule, so a fragment decides neither rule and the French word decides both the way the English one does. The 35 come out as the brain their file says they are, a stack that really does say both still comes out as both, and a neck named without a spine or a brain beside it reaches the rule that names it. The pack is version 0.1.5.

- A zero echo time decides nothing by the vote either, which is the route it was still deciding by. The guards the base windows were given reach a rule and not a pass, and a re-run over the same archive found the same phase-contrast study's 297 one-image fragments still called T1w on 288 of them. The path is `physics_vote`: closing the window left the base empty, an empty base is what makes a stack a target of the vote, and the vote reads the echo time again through its key, where 0.0 is binned to the nearest 5 ms and lands in the bin the short echo times of gradient-echo anatomy sit in. The flow study's own whole series, which do have an echo time and which a window therefore judged, were the neighbours it was answered from, so the wrong answer came back with a vote's confidence instead of a window's and nothing said a zero had decided it. A key dimension can now declare that a zero on it is not a measurement, `zero: absent`, and a zero there bins as a hole, which matches only a hole: a stack with no echo time votes among stacks with no echo time and usually among none at all. The MRI pack declares it of the echo time alone, because a repetition time, an inversion time and a flip angle of zero are as impossible but nothing measured says what declaring them would move, and a key is shared by every stack in an archive. The fragments now come out as what the pack can honestly say about them, the flow technique and the misc directory type with no base at all, and they stay the one question the split already raises about them. The pack is version 0.1.4.

- A zero echo time is not evidence of a short one, and a split that leaves one image in every stack says so. On a run over an archive, one phase-contrast study came out as 297 stacks of a single image each, every one of them an anatomical T1w acquisition: the series split on the echo number, which varies per image on a flow study, and the base contrast was then decided by the window that reads a very short echo time, on a series whose echo time is 0.0 because there is nothing to measure. The verdict was written at 0.70, which is the confidence the pack asks below, so nothing was flagged, and that one study became 279 of the archive's 339 stacks holding the `t1w` role. Two things are fixed. Every window in the MRI pack whose evidence is that a time is *small* now asks first that the time was measured at all: the gradient-echo and spin-echo windows, the FLAIR and dual-echo ones and the EPIMix route, where an absent value already failed the comparison and a zero one did not. And a split that leaves a stack holding one image, on a series split into four or more such stacks, is a question of its own, `split:one_image_per_stack`, carrying the reason the series split, collapsed into one item per reason rather than one per stack; a series whose split gives each stack its images raises nothing, and a stack the pack has ruled out is still nobody's question. The pack carries the three cases that say what a zero decides, which is nothing, and is version 0.1.3: one version for both of the changes this wave makes to its knowledge, the second text before it and the guards here.

- A release writes no session the session layer did not derive, and an ask and a selection count one archive the same way. A series carries the subject its own files named and a study carries the subject the study's files named, and the two part company wherever an archive re-linked a series under somebody else's study: the subject that is left owns series and no study, is on no timeline, gets no session and is an open question, `identity.no_study`. The release read the session label off the study alone, so it borrowed that other subject's sessions and wrote the disowned subject into `ses-` directories no scheme produced. On a run over an archive the scheme derived 44 sessions over 39 subjects and the tree came out with 45 session directories, two of which belonged to a subject the engine itself called incomplete, so a released dataset carried structure nobody derived, for somebody the engine had already said it could not place. A label is now read only from a session of the stack's own subject, and a subject that owns series and no study is refused rather than named, on the session layer's own test: its stacks are recorded in `release_absent` as `no_session` with the reason, counted among the stacks the release left out, and the subject is named in the report, so a person who selects that subject sees it counted by the selection, no directory of it in the tree, and a line saying how many of its stacks were refused and that `identity.no_study` says why. A study of a subject that does have studies but that carries no date is unchanged: it is on no session either, and `unknown` still says what it is, because it borrows nobody. The same disagreement made an ask and a selection over one archive give different numbers of subjects, 38 against 39, because the ask reached the subject and the session through the study while the selection reached them through the series. Both now read the series, which is the row that carries the subject a stack's own files named, so a stack is never counted under another subject nor rolled up under another subject's session, and the count a selection prints is the count an ask holds.

### Added

- A stack says what it covers. The fingerprint has always carried what one slice looks like, the rows, the columns, the two pixel spacings, the thickness and the spacing between slices, and never how many slices there were nor how far they reached. Measured over 437,069 classified stacks of a legacy archive, the number of slices alone is what separates 3,610 names carrying 9,905 stacks, more than every timing parameter together: two prescriptions of one protocol over a different extent, wearing one name and handed a run index that says they are the same acquisition twice. Four columns answer it. `n_slices` counts the distinct positions the stack's images sit on, from `SliceLocation`, so a dynamic series of twenty repeats over thirty slices covers thirty and not six hundred; `slice_span_mm` is the distance from the first to the last; `coverage_source` says which evidence answered, `slice_location` or `none`, so a stack whose files never placed their slices reads as unmeasured rather than as a stack of no slices; and `acquisition_matrix` is the last of the four geometry fields the survey names that the fingerprint did not already hold. A fact meant to tell two stacks apart has to be stable, or every pair looks different and the failure is only the mirror of the one it was meant to fix, so two tolerances hold it still: inside a stack, positions within a hundredth of a millimetre of one another are one slice, clustered from the lowest up rather than rounded to a grid so that two values a hair apart cannot fall either side of a boundary; and between two stacks the comparison asks for equal counts and extents within the wider of a millimetre and a hundredth of the larger, and answers that nothing differs where either side measured nothing. The slice count and the extent are fields a comparability level may compare exactly, round to a step of its own or ignore, which is where a tolerance between two stacks belongs; no level in the MRI pack names them yet and no verdict moves in this release. A pack and the ask can both read all four.

- The fingerprint says which derivation wrote a row. A row was fresh while its stack had gained no instances, so a build that learned a new fact left every row an older build wrote exactly as it was, with the new columns empty and nothing saying so, until somebody thought to pass `--force` over the whole registry. Each row now carries `fingerprint_revision`, the derivation that wrote it, and a row from an earlier one is stale however many instances its stack still has. An existing registry needs nothing said to it: opening it migrates the columns in, and the next `nils fingerprint` or `nils intake` derives every stack again and fills them.

- A stack says which coil received it. A series is split into one stack per receive coil, and has been since the digest was written: the engine reads `ReceiveCoilName`, decides on it that these are two acquisitions and not one, and then keeps the value nowhere a classifier, an ask or a name can reach, so it manufactured a difference it could not state. Measured over a legacy archive, the coil is the only thing separating 1,082 colliding names carrying 2,412 stacks, and it differs somewhere inside 5,504 of them. The fingerprint now carries `receive_coil_name`, from the stack's own row and never the series', because a series that split over two coils holds one of them and attributing that one to both stacks would be worse than holding nothing. The value is the element as the file writes it, from `ReceiveCoilName` and, in an enhanced object, from the MR Receive Coil Sequence of the functional groups: a vendor's own name for a coil, a head array from one scanner and a short code from another, and no vocabulary is imposed on it here. The element is optional and about half of the stacks of a real archive carry nothing, so the column is null there, which is the honest answer and the same one the split already gave: those stacks were never split on a coil either. The derivation's revision moves with the column, so a registry that already has fingerprints fills it on the next `nils fingerprint` and nobody has to know to pass `--force`.

- The identities an image type states are axes, and the flags the pack parsed and read nowhere now decide something. Measured over the 437,069 classified stacks of a legacy archive, 17,065 of them, 3.3 per cent, carry a token in `ImageType` that changes what the image is and that no axis of the pack read, and in 2,829 colliding names the tokens that differ are ones nothing ever looked at. The largest was already parsed: `COMPOSED` and its five short spellings tell 2,525 colliding names apart, more than any other single fact in that archive, and they went into a flag called `is_composite` that no rule mentioned. A composed image is now the construct `Composed`, so an image stitched from several stations and the station images it was built from no longer agree on every axis there is. `MEAN` is the same story on 1,154 stacks in a dead `is_mean`: it is the image the scanner writes beside the echoes it combined, always a series of its own, agreeing with its per-echo siblings on everything the pack holds and often carrying no echo number at all. It is now the construct `EchoCombined`, and it reaches that through the susceptibility route as well, which is where 1,084 of those stacks are. `MAVRIC` and `MAVRIC_COMPOSITE`, in a dead `is_mavric`, are the technique `MAVRIC`, and the second is also a composed image of one, which is what that spelling says. `TTEST`, which separates 209 colliding names, is the construct `TTestMap`: a statistic over a series rather than an image of a person. The quantitative maps were worse off than unread. `QMAP T1`, `QMAP T2` and `QMAP PD` have been parsed apart since the pack was written and the construct axis read none of the three, so every stack whose image type said `QMAP` came out as a T1 map and a T2 map at once, whichever it was. The maps are now one exclusion group in which a map that names its quantity beats one that says only that it is a map, `FLIP ANGLE MAP` reaches `B1map`, which is what BIDS calls it too, and `has_pd_map`, `has_b0_map`, `has_b1_map` and `has_qsm` reach the values they were named after. The projection spellings that had no predicate at all join the ones that had: `MINIMUM`, `MAXIMUM`, `HD MIP`, `MAX_IP`, `MIPT`, `COLLAPSE`, `PJN` and `CPR`, 549 stacks between them, and the substring test that looked for `PROJECTION IMAGE` now looks for the part that survives the truncation the archive writes on 326 more. Four flags went the other way. `is_dixon_water`, `is_dixon_fat`, `is_dixon_in_phase` and `is_dixon_out_phase` said the Dixon part a second time, where `Water`, `Fat`, `InPhase` and `OutPhase` on the construct axis have carried it on all 2,773 stacks that state it since that axis was written; a second spelling of a decided fact is how two parts of one program come to disagree about it, so the four are gone and the cases that pin the part now assert the axis. Where any of this belongs in a filename is the next slice's question: this one is about what the row says. The pack is version 0.2.0, because a vocabulary is a contract and a question asked of one version must not be answered in another's words.

- Each axis sits where it belongs in a BIDS name, and nothing the standard refuses is dropped. Measured over 836 named stacks of the record 34 corpus and against a legacy archive of 437,069 (`studies/2026-09-19-bids-naming/`), five facts were in `acq-` that the standard has an entity for and four were being thrown away because the suffix in hand would not take theirs. The scanner's pipeline and the reconstruction kinds, MPR, MIP, MinIP, denoised, filtered and ORIG, are `rec-` now, which every suffix group the pack writes admits and which separates not one pair less than `acq-` did; the contrast is `ce-`, the complex part `part-`, the echo `echo-`, the phase-encoding direction `dir-`, and the inversion comes with the suffix as it did. What the schema refuses a suffix is no longer dropped, which used to make two different acquisitions share one name and call the second a repeat of the first: the fact is spelled into `acq-`, which is free-form, as the entity's own word and its value, so a post-contrast diffusion image reads `acq-...CeContrast` and a magnitude ADC map reads `acq-PartMag`. Where the label carries the fact already the label is left alone, which is what happens to magnetisation transfer: BIDS gives `mt-` only to `MTR`, `MTS` and `MPM`, and the `MT` modifier is an `acq-` token of this pack, so the name says it once. Either way the release counts the refusal by entity, in the report, so a tree says how often the standard had no slot for something the archive states: over that corpus 15 contrasts, 4 echoes, 3 parts and 3 transfers, closing 9 of the pairs that were sharing a name. The body part stays in `acq-`, because it is what separates 22 otherwise identical pairs and a filename has to be unique, and it now also goes where the specification keeps it, the sidecar's `BodyPart`, written into the converter's JSON after the conversion and before the tree's own digest, so a re-run sees no change. And the axes `acq-` may read are the pack's to declare rather than a list inside the engine: the quality axis this wave added could not reach a filename at all, because naming knew six axis names and that was not one of them. A pack that declares an axis and gives its values tokens has named with it, and a `from` that is neither an axis nor one of the two fields the stack measures itself, the orientation and the acquisition type, is refused when the pack loads rather than contributing nothing in silence.

- A release says what a name carries, in two modes, and records which it wrote. **BIDS** is the default: what the standard's entities carry, in the entities, and the rest in `acq-`, which is what a validator reads and a tool joins on. **Informative** carries every axis the pack declares, including the ones an entity already says, for a tree read by people rather than tools: in the BIDS layout that is a longer `acq-` label, still a legal BIDS label because `acq-` is free-form, and in the descriptive layout it is section 9.1's grammar, which has no entities to carry anything. A person chooses with `nils release --naming bids|informative`, at the command line or through the release door; unasked it follows the layout, `--naming bids` on a descriptive tree is refused because that tree has no entities, and the mode is written on the release row beside the layout, so a re-run of a release writes the names that release wrote. The pack says which mode each group of `acq-` tokens is in, `modes: [informative]` on the ones the standard has an entity for, so the BIDS name says a fact once and the informative name says it at all. And the informative echo suffix is per stack: it used to be all or nothing over a bucket, so one stack without a measured echo number dropped the suffix for everybody and the whole bucket fell to a `_1`, `_2` counter, which over 836 stacks is 78 buckets and 453 stacks, 6,997 of whose pairs differ in nothing but their echo. Each stack is named from its own echo now and what still shares a name is counted after that, which leaves 448 such pairs instead of 7,451.

- A stack says what its own file says is wrong with it, on an axis of its own. Two more tokens answer neither of the questions the other axes ask. `NAVAIL`, on 105 stacks, is a derived image the scanner produced without one of the inputs it is computed from, and it separates 93 colliding names; `DISTORTED`, on 19 stacks, is a vendor's word for an image its distortion correction did not reach, written beside the `DIS2D` and `DIS3D` siblings that it did, and it separates 15. Both were parsed into flags nothing read. Neither says what the image is, so neither belongs on an axis that answers that: they are `quality`, a multi-valued axis with the values `InputUnavailable`, `Distorted` and `Encrypted`, decided after the axes that say what a stack is and blank on the ordinary stack, which is most of them. The third value is `ENCRYPTED`, 92 stacks whose pixels nothing downstream can read. It is said here rather than by ruling the stack out, because what arrived is still a fact about the examination and what it costs is the conversion; the disposition now refuses that conversion and names the reason, and the stack keeps the disposition it would otherwise have had. Nothing else about what is ruled out changes. `is_qa`, the flag that would stop 21 standard deviation and coverage maps being classified as images of a person, is still deliberately read by nothing, and says so in the pack: wiring it is a change to what is excluded, and that belongs with the rest of the exclusion tail rather than here.

- The quarantine says what it set aside. About one file in a hundred of a study directory is an object NILS does not take: a walk of 120 directories and 140,326 files found 1,677 of them, most of a whole study's radiologist annotations in one case, and the report a person read said `unsupported_sop_class` with a UID beside it. A UID is not an answer to what the archive held, and the question a reader actually has, whether anything was lost and of what sort, could only be answered by looking the UIDs up one at a time. Every quarantined file now carries a kind in words, derived from what the refusal already recorded: the family of its SOP class where the class is the reason, secondary capture, presentation state, structured report, key object selection, registration, fiducials, segmentation, raw data, encapsulated document, waveform, parametric map, another image class, another standard class or a private class, and what the class itself means otherwise, not DICOM, unreadable, a broken header, no identifier, no modality or another modality. The digest's report gains a `set aside` block, a line per kind with its count and the classes inside it named as the standard names them, in the printed report and in the batch's stored counts, so a run says forever what it left behind. The review item of each quarantine class carries the same kinds beside its count, so the queue reads as what was set aside rather than as a number. And `nils quarantine list` prints the kind beside the class for each path, with a summary line above them and the counts in `--json`. Nothing new is read from a file and no column is added: the kind is a reading of the class and the UID a refusal already wrote down, so a registry filled before this answers the question as well as one filled after.

A release pushes `ghcr.io/kineuro/nils:<git tag>` and a git tag begins with a `v`, but the updater strips that `v` from every version it holds, so the wizard asked for `nils:1.0.0-alpha.2`, a tag that was never pushed. Every container install fell back to building the image locally from the release binary, and said nothing about it. One function names an image now, and the run commands, the compose file, the quadlets, the state file and `nils update` all go through it. Both images are public and pull without an account.
- An engine that starts before the issuer it trusts. In `local` mode the desk mints the tokens and the engine verifies them, and the desk cannot start before the engine it proxies to: they need each other. The engine fetched the desk's keys at startup and exited when the fetch failed, which in a pod is every time and on a machine is every boot that loses the race. A JWKS file that cannot be read is still a fault in the configuration and stops the engine, because the file should be there. A JWKS URL that does not answer is a matter of order: the engine says so in a sentence naming the issuer, starts holding no key of it, and asks again when the first token arrives, with the refetch floor waived while it holds none so that token is not refused for a minute.
- The rule packs on a machine install. The binary carries none and the wizard fetched none, so an engine installed on a machine started saying `packs none` and would have refused to digest anything. The release has carried `packs.tar.gz` beside the binaries all along, and only `nils update` ever unpacked it, over a directory a fresh install had never made. The wizard now unpacks it into the share directory of the prefix the engine binary sits in, `~/.local/share/nils/packs` for the one line installer's usual place and `/usr/local/share/nils/packs` for a root install, which are places the engine looks with no flag at all, so `nils digest` run by hand finds them too. Where that prefix cannot be written they go in the registry's own directory. Failing to fetch them does not stop the install: it says what is missing, what it costs, and where to put a pack directory instead.
- A key fetch that could stall a request handler. Now that the engine survives an issuer that is not up, it asks again on a request, and that ask had no bound on it: an issuer that is unreachable rather than refusing could hold a worker for whatever the default connect timeout happens to be, and every request would pay it in turn. The fetch is bounded at two seconds to connect and four in all; the stamp that paces the asking is taken and unlocked before the fetch, so a request arriving mid-ask is refused at once instead of queueing behind the network; and while the engine holds no key of an issuer at all it asks at most once every five seconds, which is longer than a fetch can take, so two are never in flight.
- A docker install that could not write what it mounted. Podman remaps the user and `:U` hands the container ownership of the mount; docker does neither, so the image's own user could not write a directory belonging to the account that ran the wizard, and the install stopped at `Permission denied` on the registry's key store before a registry existed. Every docker run is told to be this account now: the two that make the registry, the two that run the parts, and both services of the compose file. Podman is untouched, because it already does the right thing.

A SQLite registry is read by its declared types rather than as text, since SQLite spells a REAL with 15 significant digits and a float32 widened to a double needs 17, which made hundreds of series differ on the spelling alone. The thirteen stack-signature columns of the series tables are derived from the catalogue as the engine derives them, and a divergence of one of them in a series with several stacks on either side is grouped apart (` (multi-stack)`) and classed `accepted` by the tool itself: the series row carries the first instance's value on both sides and which instance is first follows the walk order; the same field in a single-stack series still needs a rule. - A row's fields are decided, not raced (Wave 1 spec, §8 and §9.1, slice 3 amended in slice 7). Where two files of one subject, study or series disagree on a column, the row keeps the smaller value in the catalogue's canonical text order instead of the first one written, on every column of those rows; the fill rule covers every column too. The registry no longer depends on the order the walk and the workers gave the files, which the first gate run showed to be real: single series carry up to twenty-six spellings of `sequence_name`, two acquisition matrices, two slice spacings and two orientations. `min` needs no bookkeeping, so a resumed run, a late batch and a second digest of one tree reach the same row; the writer reads a field's stored value once, the first time that field of that row is disagreed about, and keeps it with the cached row.
- A person may hold several identifiers of one type (Wave 1 spec, §7.3 and §7.4, slice 4 amended in slice 7). `nils linkage import` files any number of identifiers of one type on one subject instead of refusing the second, and counts the ones that joined a code another identifier already named: a personnummer is not for life, since a temporary number becomes a permanent one when residency is granted, several temporary ones may come before that, and the permanent one changes when a legal sex change does. Only an identifier that maps to two codes is still refused, and two identifiers that derive one code by the scheme's function are still a collision. The identity rule gained `code: verbatim`, which files the value it reads as the subject code instead of deriving one, for data pseudonymized before it reaches us; it requires a pattern on every field, so a value that is not shaped like a code is never filed as one, and a file that does not match takes the fallback as always.
- Files whose elements declare a length their VR cannot hold are read, not quarantined (Wave 1 spec, §6.1, slice 2 amended in slice 7). One vendor's private block writes a `UL` of six bytes, where a `UL` takes four; `dicom-rs` reads the values that fit but counts the whole length as consumed, so the stream runs two bytes behind and the file looks truncated. The reader now repairs such a file in memory when the first read failed as truncated: it walks the header, rounds each impossible length down to the values that fit, drops the surplus bytes and reads the repaired copy, counting a `ragged_length` diagnostic. The file on disk is never touched. On the mix corpus this recovered 1,996 files of 196,086, and with them 69 series, 47 studies and 32 subjects.
- The budget, measured (Wave 1 spec, §14, slice 8; §12.5 and §12.6). On an 8 vCPU / 64 GB virtual machine reading the corpus from the storage server over NFS, from a cold cache, v0 digests one study's raw tree of 497,150 files in 981 s at 507 files/s and 5.78 GiB, and v1 in 87 s at 5,713 files/s and 0.83 GiB, with the same counts on both sides: eleven times the rate at a seventh of the memory. On Postgres 16 v1 takes 93 s; a second pass over the unchanged tree takes 4.2 s. The gate of §12 passes on that host too, every bar. A `bench` job in CI writes 200,000 instances from a seed, digests them and fails the build when the rate falls below 80 percent of the recorded baseline or the memory rises above its cap (`engine/benches/`).
- The fingerprint (Wave 2 spec, §4 and §13, slice 1). A new crate, `nils-classify`, and a new table, `stack_fingerprint`, added by migration 2 so that a registry written before it opens under this binary without being rebuilt. `nils fingerprint` derives one row per stack: the six text fields v0 joins, each folded and once more as the join (Unicode NFKC, whitespace collapsed, **case kept**, because a pack's first normalizer step is a case-sensitive removal); the multi-valued fields as read, since a parser declares its own tokenizer; the physics, the stack's own value where it has one and the series' otherwise; the shape, the provenance and the contrast administration; and v0's field of view, from the stack's first instance **by SOP Instance UID** rather than by row id, which is Wave 1 §15's open item closed on the deterministic side. It is a job like the digest, with the same takeover of a dead one, a heartbeat, a stop between windows and a resume that is a predicate over columns: a stack already derived whose instance count still agrees is skipped, one that gained an instance is derived again, and `--force` overwrites. What the fingerprint does **not** hold is the decision the slice turned on: no flags and no semantic normalization, because both are derived by a pack's grammar. The fingerprint holds what is true of the file; a pack holds what is true of the knowledge, and correcting the token map is then a pack version rather than a re-extraction of the archive. It does carry one thing v0 computes and never reads: **why a series split**, the first signature column its stacks disagree on in v0's order, which three of v0's flags test for and none of them ever receives. v1's derivation agrees with v0 on all 2,165 series of the nmosd corpus and on 2,559 of the mix corpus's 2,567; the eight are v0's own, and their cause is named: v0 writes the key in its sort step and not in extraction, so all 19 multi-stack series in the archive without one are exactly the 19 that were never classified. On the development container the pass costs 0.8 s for nmosd's 2,534 stacks and 0.4 s for the mix corpus's 4,120, at 0.08 GiB, against the 30 s and 87 s their digests took.
- The pack loader (Wave 2 spec, §5 and §13, slice 2). A new crate, `nils-pack`, which knows nothing about a registry: a pack plus a stack yields facts, which is what makes a pack testable from a fixture and shippable by someone who has never seen our schema. It loads a manifest (name, semantic version, contract, modality), the parser and flag layers, and the pack's editable **buckets**; it refuses a contract it does not implement, a version that is not semantic, a name that resolves to nothing, a pattern that will not compile, a flag that depends on itself, and a parser declared twice, each **by file, line and path**, because a pack is written by someone who writes vocabulary rather than Rust. **Overlays** (C2) are provenance-scoped and refused when scoped by a selection; the merge is v0's rule exactly, duplicates dropped case-insensitively with the first spelling kept and the order of writing preserved, since v0's contrast vocabulary contains terms whose leading space is load-bearing. The pack's own **corpus runs at load** and its failure is the load's failure, which is what makes a pack from elsewhere safe to install. Whose cases judge what was settled while building: the pack's corpus judges the pack, un-overlaid, and an overlay carries its own cases and is judged by those, because running the author's claims against a site's amendment makes the claims a constraint on the site. `packs/mri/` holds the parser and flag layers the C11 prototype verified against v0 over 518,365 stacks, now with 18 cases of its own; `nils pack list | show | validate` read them.
